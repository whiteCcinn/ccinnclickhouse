# Security Policy

## Supported versions

Security fixes are released for the latest minor version of CcinnClickHouse.

| Version | Supported |
|---|---|
| 1.0.x | ✅ |

## Reporting a vulnerability

Please **do not open a public issue** for security problems.

Report vulnerabilities privately through GitHub's [private vulnerability reporting](https://github.com/whiteCcinn/ccinnclickhouse/security/advisories/new). Include:

- a description of the issue and its impact,
- steps to reproduce (ClickHouse version, connection options, sample data if relevant),
- any suggested fix.

You can expect an acknowledgement within a few days. Once a fix is available, we will publish a release and an advisory crediting the reporter (unless you prefer to remain anonymous).

## Advisory: read-only guard bypasses in 1.2.0 and earlier

The read-only guard behind MCP `run_query` and read-only editor batches could be made to run `file()`, which `readonly=1` does not stop (on 22.8 and 24.8 not even for a user without grants). Fixed in 1.3.0. There are five bypass classes:

1. **Unicode whitespace** that ClickHouse skips (U+00A0, U+FEFF, U+200B …): `SELECT 1,<U+FEFF>file('x')`.
2. **`//` comments**: ClickHouse reads `//` as a line comment, the guard read two `/` operators.
3. **The automatic LIMIT**: inserted after a bare `#` or a lone `$`, it hid a `file()` call that the guard had judged to be inside a comment.
4. **Escaped quoted names**: ClickHouse decodes `\xHH` and `\N` in quoted names: ``SELECT 1, `\x66ile`('x')``.
5. **Function references without a call**: `APPLY` names a function without `name(`: `SELECT * APPLY(file) FROM (SELECT 'nonexistent.txt' AS p)` opened the file under `readonly=1` on 22.8, 24.8 and 26.8, and on 22.8 and 24.8 for a user with no grants. The same holds for `APPLY file`, ``APPLY(`file`)``, `COLUMNS('p') APPLY(file)`, `t.* APPLY(file)`, `* EXCEPT (q) APPLY(file)` and chained transformers. On 26.8, higher-order functions also take a bare function name: `arrayMap(file, ['x'])`.

Upgrade to 1.3.0. Until then, give AI access only to a ClickHouse user with a read-only settings profile and `SELECT` grants only (see below); on 26.8 such a user lacks `READ ON FILE`.

## Scope and design notes

- Passwords and SSH secrets are stored in the macOS Keychain; saved profiles on disk (0600) never contain them. Credentials travel in the `Authorization` header, never in URLs; redirects are not followed.
- HTTPS uses the system trust store, optionally extended with a private CA per connection. Through an SSH tunnel, certificates are still verified against the server's real host name. "Skip certificate verification" exists for test setups and is clearly marked.
- Read-only connections and read-only AI access are enforced by ClickHouse itself (`readonly=1` on every request, with `getSetting('readonly')` verified on the actual request path when connecting — a proxy that drops the parameter, such as chproxy, makes the connection fail closed) and, in addition, by the app's read-only guard, which refuses anything that is not clearly a read, any function that reaches outside ClickHouse and any per-query `SETTINGS` before it is sent. A bypass of either layer is in scope.
- Read-only AI access requires a ClickHouse user with `SELECT` grants only.
  - Before every call, read-only AI tools read the user's grants with `SHOW GRANTS` and the effective `readonly` level, on the request path the call takes. If either cannot be read, they refuse.
  - They refuse a user holding `SOURCES`/`FILE`/`URL`/`REMOTE`/`S3` …, `SYSTEM`, access management, `INTROSPECTION`, `ALL`, roles (whose privileges `SHOW GRANTS` does not list) or a grant option, unless the connection explicitly allows it. No SQL text guard can contain such a user: `readonly=1` does not stop `file()`, `url()`, `SYSTEM` or access management.
  - AI access calls only reviewed functions (deny by default). The catalog (`AIFunctionCatalog`, generated by `scripts/gen-ai-function-catalog.py` with a header saying how) is the union of what 22.8, 24.8 and 26.8 ship in `system.functions`, with `case_insensitive` and `alias_to` respected. From it, every function that reaches outside ClickHouse, reads objects or request data by name, introspects the binary, changes state or is internal is removed, together with its aliases. An aggregate function may carry any chain of combinator suffixes.
    - The guard checks every way a statement names a function, in any clause and at any depth: `name(` (including parametric `quantile(0.5)(x)`); the name after `APPLY`, with or without parentheses, quoted or chained; a bare first argument of a higher-order function (26.8 runs `arrayMap(file, …)`); and the string naming the aggregate in `arrayReduce`, `arrayReduceInRanges` and `initializeAggregation`.
    - A construct whose function cannot be read is refused: `APPLY` of an expression, a higher-order function's first argument that is neither a lambda nor a name, or a parenthesised expression called like a function.
    - Table functions fall into four classes: external (refused everywhere, for both audiences), allowed (generators and inline data), reviewed-local (read tables by name; editor only), and AI-refused.
    - A newer server's new functions are refused until an update reviews them, and an integration test fails on any function, table function or privilege a supported server ships that the catalog does not classify.
    - `dictGet` is allowed by design: it reads dictionaries whose sources an administrator defines.
  - A settings profile can change how the server parses a statement or resolves its names. Under `dialect = 'polyglot'` with `polyglot_dialect = 'postgresql'`, `'\'` is a complete string, so `SELECT '\', (subquery) --'` runs a subquery that the guard sees inside a string. `implicit_table_at_top_level` gives `SELECT query WHERE …` a table without any table name. Read-only requests therefore send `dialect = clickhouse`, `implicit_table_at_top_level = ''`, `implicit_select = 0`, `polyglot_dialect = ''` and `enable_json_ast_dialect = 0` wherever the server accepts settings. Every read-only path (connecting, every AI tool call including the metadata tools, every editor batch) reads the effective values from `system.settings` together with `readonly`, and refuses when one differs or cannot be read. A setting a version lacks counts as its default. A profile with `readonly = 1` forbids the override, so such a profile is refused. An integration test fails on any setting whose name or description concerns a dialect, the parser or an implicit table that is neither verified nor reviewed.
  - String literals the app builds (metadata tools pass AI-supplied names) double `'` rather than writing `\'`, which a dialect without backslash escapes would end early.
  - The privilege check follows `system.privileges`' parent hierarchy (the server's own when readable, a pinned one otherwise). A privilege is risky when it or any ancestor is (so `aiGenerate` counts under `AI FUNCTIONS`, and so does a future child of a risky group), and a privilege the hierarchy does not know is risky.
  - For AI access the guard reads `system` through an allow-list of schema and diagnostic tables, and table functions through an allow-list of generators. Every other system source (`query_log`, `processes`, `mutations`, `users`, `named_collections`, renamed log tables, `loop`/`merge`/`cluster` over `system`, `SHOW PROCESSLIST` …) is refused in any form. Credentials are not the only thing literals hold, so the tools that show other sessions' SQL return digests. Exactly:
    - **Statements** (running queries, query log, mutation commands, the distributed DDL queue): every string literal and heredoc, every number, every double-quoted name (a mistaken string: `WHERE x = "secret"`) and every unterminated string, quoted name or heredoc (to the end of the text) becomes `?`. Comments are dropped. Bare words, backticked names, keywords, operators and layout stay.
    - **Error texts** (the query log's `exception`, a mutation's `latest_fail_reason`, the replication queue's `last_exception`), in three steps:
      1. Errors repeat some values unquoted (`Cannot parse uuid …`, `Unknown setting …`, throwIf messages), so every occurrence of the literal values of the error's own statement becomes `?`, longest first. These values are string literals (as written and decoded), heredoc bodies, quoted names and the rest of the text after an unclosed heredoc, each of 3 characters or more, plus numbers with 4 or more digits. For the replication queue they are the values of the table's active mutations; if those cannot be read, the error is withheld.
      2. Statement echoes are dropped: `failed at position …`, `in scope …`, `while processing query: …`, and the data after `here:` / `before:`.
      3. Every remaining literal, number and quoted name (backticked too) becomes `?`.
    - **Not masked:**
      - a value written unquoted (`WHERE token = abc123` stays visible; masking every name would make digests useless);
      - a value shorter than 3 characters, or a number of up to 3 digits, repeated in an error;
      - text an error derives from a value without repeating it.
  - AI access never receives object definitions, on any version (deny by default). 22.8 prints credentials in them, 24.8 still prints the ones in URLs, 22.8 and 24.8 inline view queries into `EXPLAIN SYNTAX`, and 26.8 prints view literals in plans. The guard refuses the definition columns (`create_table_query`, `engine_full`, `as_select`, `create_query`, `view_definition`, `query` where `system.projections` is read, …) with any qualifier, alias or quoting; SHOW outside an allow-list of listing forms (so `SHOW CREATE`, `SHOW TABLE`, `SHOW VIEW` and `SHOW FUNCTIONS`); `EXPLAIN SYNTAX`, `EXPLAIN QUERY TREE` and EXPLAIN inside another query; any `*` but `count(*)`, and `COLUMNS(…)`, in a query over `system.tables`, `system.databases`, `system.functions`, `system.projections` or `information_schema`; and `FORMAT` clauses, so every result reaches the tool as text it can mask. `describe_table` returns columns, keys and the engine name. Quoted strings in EXPLAIN results become `'?'` (numbers stay). Credentials are masked in every string the tools return, precisely so that data is not altered: URL passwords (a user alone stays), values of credential-named keys and literals (`password=…`, `PASSWORD '…'`, `kafka_sasl_password = '…'`; never a bare `KEY`), and, in definition-like text (`CREATE …`, `ENGINE = …`) only, the credential arguments of table functions and engines. A result with masked values carries `"masked": N`. Error texts are masked thoroughly.
  - Known limitations of the definitions rule:
    - Views or dictionaries that an administrator builds over system tables are invisible to the guard, which sees only their names. AI access reads them like any other table; grant the AI user `SELECT` only on what it may see.
    - EXPLAIN results keep their numbers (granules, rows and marks are what a plan is for), so a numeric literal inside a view's definition (`WHERE pin = 4242`) can still appear in a plan. Quoted strings never do.
    - Column default expressions (`system.columns.default_expression`, the `default` of `describe_table`) are shown as schema. They cannot call table functions, so a credential appears there only if someone writes it as a literal.
    - Unqualified names are judged by the current database: the call's, else the connection's, else the one the server reports when connecting (`currentDatabase()`, read by the connection probe). Only if none is known are they taken to be in no particular database, so the `system` allow-list and the `information_schema` `*` rule do not apply to them. Qualified names (`system.query_log`, `information_schema.views`) are always checked.
  - MCP tools refuse any argument other than `sql` that holds a control character (Unicode Cc: NUL, C0, DEL, C1) before anything is sent. Identifier quoting escapes control characters as `\xHH` rather than dropping them, and URL parameters are strictly percent-encoded, so the server reads exactly the name that was checked.
  - ClickHouse decodes `\xHH` and `\N` in quoted names (`` `\x66ile`('…') `` calls `file()`). The guard refuses any quoted name containing a backslash rather than decoding it. It also refuses any name (bare, keyword or quoted) holding one of the 19 letters whose upper, lower or title case contains an ASCII letter (`ß İ ı ŉ ſ ǰ ẖ ẗ ẘ ẙ ẚ K ﬀ–ﬆ`, derived from Unicode and pinned by a test): ClickHouse does not fold them, but case-insensitive comparisons would read `` system.`ſettings` `` as `settings`.
  - Scalar `file()` needs no FILE grant on 22.8 and 24.8: any user may read files under `user_files`. There the text guard, which refuses `file()` everywhere, is the barrier, not the grant check. 26.8 requires `READ ON FILE`.
  - The guard checks the exact text sent, after the automatic `LIMIT` and any EXPLAIN head are added.
- **Recommended deployment for AI access:** a dedicated ClickHouse user whose settings profile is read-only and who holds `SELECT` grants only (no `SOURCES`/`URL`/`FILE`/`REMOTE`/`S3` grants). The server profile — not a URL parameter — then enforces read-only access, so it holds behind proxies that drop parameters (chproxy) and independently of the app. The README and Settings → MCP give the SQL.
- Each MCP tool call is a separate stateless request without a server session, so `SET`, `USE` and temporary tables never carry from one call into the next.
- SQL written to the query history and the MCP audit log (`mcp-audit.jsonl`, 0600) is redacted: `IDENTIFIED … BY`, `PASSWORD`, credential-like settings and named-collection values, credential arguments of table functions/engines (`mysql`, `postgresql`, `remote`, `s3`, …) and `user:password@` in URLs become `***`.
- SSH tunnels use the system `/usr/bin/ssh` with `StrictHostKeyChecking=accept-new` (changed host keys are rejected). Secrets reach `ssh` through a short-lived 0600 file, never the environment or argv; key mode is public-key only and agent mode never sends a stored secret.
  - The tunnel never uses or becomes a shared `ControlMaster` connection (`-o ControlMaster=no -o ControlPath=none`), so the forwarded port belongs to the tunnel alone and closes with it.
  - **Known limitation:** a `ProxyJump` (or `ProxyCommand`) in `~/.ssh/config` starts its own `ssh` for the jump host. That `ssh` follows your configuration, including `ControlMaster` and `ControlPersist`, so the jump hop may use or become a shared connection that outlives the tunnel. Set `ControlMaster no` for jump hosts you use with CcinnClickHouse if that matters to you.
- `CCINNCLICKHOUSE_TEST_PASSWORD_<PROFILE-UUID>` is a **test-only** password source for the MCP subprocess tests; do not use it outside test environments.
- Statements built by the app (metadata, `KILL QUERY`, `KILL MUTATION`, `SYSTEM RELOAD DICTIONARY`) quote identifiers and literals; issues that allow injecting SQL through object names are considered vulnerabilities.
- Update checks contact only `api.github.com` and `github.com`, send no personal data (the User-Agent is `CcinnClickHouse/<version>`), and run at most once a day unless you check manually. A downloaded disk image is accepted only from this repository's download URL for the same release tag, at the size the release lists, and with the SHA-256 published in that release's `SHA256SUMS.txt`. The checksum guards against corruption and truncation, not against a compromised GitHub release; authenticity relies on HTTPS to github.com. The app never replaces itself; you drag the new version into Applications.
